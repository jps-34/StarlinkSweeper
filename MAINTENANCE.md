# Maintenance: development, release and signing

Notes for the author. Nothing here is needed to use the script.

## 1. Repository layout

| Path | Role |
|---|---|
| `scripts/StarlinkSweeper.js` | the PixInsight script, **only source to edit** for the script |
| `python/starlinksweeper.py` | command-line version, same algorithm and constants as the script; packed into the update archive next to the script, where the dialog finds it for the parallel scan |
| `tests/make_synthetic_subs.py` | generates the synthetic validation frames (a few GB, a few minutes) |
| `tools/build_repo.py` | builds the PixInsight update repository into `docs/` |
| `docs/` | served by GitHub Pages: `index.html`, `updates.xri`, the script archive, `.nojekyll` |
| `README.md`, `README.fr.md` | English and French documentation, each linking to the other |
| `CHANGELOG.md` | one entry per published version |

The script has no `#engine` directive and runs with PixInsight's default JavaScript engine
(validated on 1.9.5). The update repository declares PixInsight 1.9.4 and later.

## 2. Initial publication (done in 1.0.0, kept for reference)

1. Build the update repository (rebuild it after every change to the script):

   ```bash
   python3 tools/build_repo.py --user jps-34
   ```

2. Create the `StarlinkSweeper` repository on GitHub (public), then:

   ```bash
   git init && git add . && git commit -m "StarlinkSweeper 1.0.0"
   git branch -M main
   git remote add origin git@github.com:jps-34/StarlinkSweeper.git
   git push -u origin main
   ```

3. On GitHub: *Settings > Pages > Build and deployment > Deploy from a branch*, branch `main`,
   folder `/docs`. The PixInsight repository is then served at
   `https://jps-34.github.io/StarlinkSweeper/`.

4. Test: in PixInsight, *Resources > Updates > Manage Repositories*, add this URL, then
   *Check for Updates*. Until it is signed, the *Allow unsigned update repositories* security
   option is required.

## 3. Signing (once and for all)

References: [Script code signing](https://pixinsight.com/doc/docs/ScriptCodeSigning/ScriptCodeSigning.html)
and [Update repositories](https://pixinsight.com/doc/docs/PIRepositoryReference/PIRepositoryReference.html).

1. **Keys**: **SigningKeys** script (shipped with PixInsight). It creates a key pair in a
   password-protected `.xssk` file. Use a very strong password, keep the file backed up offline,
   **never in Git** (the `.gitignore` excludes it).
2. **Certified developer status (CPD)**: **SubmitCPD** script, with a developer identifier, the
   public key and an e-mail address. The PixInsight team reviews the request and gets back in touch
   if needed. It is an identity check, not a code review. Without this status, the signature is
   only recognised on your own machines.

## 4. dev branch, then production

`main` = production: GitHub Pages serves `docs/` from `main`, so everything that lands on `main`
reaches PixInsight users. A new version goes to `dev` first.

Keep `scripts/StarlinkSweeper.js` and `python/starlinksweeper.py` in step: the detection constants
at the top of both files must stay identical, so that both give the same scores. `VERSION` lives in
both files as well. `docs/` (archive, digest, `updates.xri`) is generated by
`python3 tools/build_repo.py --user jps-34`.

Putting a new version on dev (example with the 1.0.1 archive):

```bash
cd <local repository folder>/StarlinkSweeper
git switch dev
git rm -rq .
unzip -o <download folder>/StarlinkSweeper-v1.0.1.zip -d <temporary folder>
cp -a <temporary folder>/StarlinkSweeper/. .
git add -A
git status                     # check the list before committing
git commit -m "StarlinkSweeper 1.0.1"
git push
```

Test in PixInsight: *Script > Execute Script File*, pick `scripts/StarlinkSweeper.js` in the local
repository. The script runs without being installed; the production version stays in place.

Releasing once validated:

```bash
git switch main
git merge dev
git tag -a v1.0.1 -m "StarlinkSweeper 1.0.1"
git push origin main --tags
git switch dev
```

Then, in PixInsight, *Resources > Updates > Check for Updates*.

With signing (later), order matters: sign `scripts/StarlinkSweeper.js` with **CodeSign**, run
`python3 tools/build_repo.py --user jps-34`, sign `docs/updates.xri` last, then commit.

## 5. Validating a change to the detector

1. Generate the synthetic set once: `python3 tests/make_synthetic_subs.py <folder>`.
2. Run the command-line version on it and on a few real subs:
   `python3 python/starlinksweeper.py <folder> --preview-all --preview <output folder>`.
   Every frame whose name starts with `sat_`, `starlink_` or `aircraft` must be flagged, the
   `clean_*` and `star_spikes` frames must not; look at the PNG previews.
3. Port the change to `scripts/StarlinkSweeper.js` (the numeric core is the section between the
   `numeric core` and `end of core` markers) and check both give the same scores on the same files.

## 6. Versions and history

* Numbering `MAJOR.MINOR.PATCH`: patch = bug fixed with no intended change in results, minor = new
  feature, major = incompatible settings or results.
* Each published version has its `vX.Y.Z` tag. The PixInsight repository (`docs/`) only serves
  the latest one; older versions stay available through git.
* Full history: `git log --oneline --decorate`.
* Getting a file from an older version:
  `git show v1.0.0:scripts/StarlinkSweeper.js > StarlinkSweeper-1.0.0.js`

## 7. Fallback: editing through the GitHub website (without git)

Keep this for small text fixes (README, CHANGELOG). Note: a change made on the website in the
`main` branch is published immediately. For a script, go through dev.

1. On the repository page, open the relevant folder, then *Add file > Upload files* and drop the
   modified files: a file with the same name replaces the old one.
2. *Commit changes*. Then run `git pull` on `main` and `git merge main` on dev.
